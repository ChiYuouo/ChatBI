# ChatBI 后端能力完善规划

更新日期：2026-10-06。

## 目标

把 ChatBI 建成一个**可评测、可定位问题、可验证优化效果的 AI 分析后端**。核心展示点是：业务问题进入系统后，身份与数据权限被正确执行，Agent 的每一步有可追踪的结果，错误能归因，改动能用同一套用例证明有效。

保留现有 React 页面、FastAPI 接口和 Python Agent。前端继续调用 `/api/v1/query`、`/api/v1/query/stream`、`/api/v1/analyze/stream`。SQL 安全校验、只读数据库账号、执行预算和用户会话仍是所有路径的共同边界。不增加 Java 服务，也不为展示技术栈引入新的 Agent 框架。

## 当前起点

| 已有能力 | 目前的证据与限制 |
|---|---|
| Text-to-SQL 评测 | [历史报告](../reports/evaluation_report.md)有 50 题、42 题结果正确；这是 2026-10-02 的旧版本数据，不代表当前版本。现有评测主要覆盖单次 SQL 结果，未覆盖完整归因链路、权限和成本。 |
| 后端安全 | FastAPI 登录与逐请求身份核验、角色/区域限制、统一 SQL 策略、只读 MySQL 账号、行数/字节/时间预算及连接池已经存在。 |
| 执行追踪 | API 返回 `X-Trace-Id`；SQLite 审计已有查询和 SQL 的开始、成功、失败或拒绝事件。尚缺检索、模型调用、规划、报告、重试的分步耗时与用量。 |
| 运行方式 | Docker Compose 可启动原前端、Python 后端、MySQL 和检索索引；健康检查可验证数据库与索引就绪。 |

以上是实施起点，不把历史 84% 当成新版本基线，也不把审计记录等同于完整可观测性。

## 工作顺序与验收

### 评测：先建立当前版本的可信基线

- 固定一份可重建的测试数据库、指标定义和功能开关；记录模型、Prompt、Schema、指标及代码版本。评测必须走与用户查询相同的 Agent 与 SQL 执行入口，不能单独绕过权限策略直接运行模型生成的 SQL。
- 整理现有 50 题并复核参考答案。新增多轮追问、复杂归因、模糊业务口径、错误输入、权限拒绝与越权 SQL 用例。将用于调优的用例和留作最终验证的用例分开，避免针对答案反复修改提示词。
- 给不同问题设置合适的判分：SQL 查询以执行结果和业务口径为主；权限用例必须验证拒绝且未触库；归因报告检查关键结论是否有实际查询结果支持。主观表述可以人工复核，不能只凭一次 LLM 打分宣称正确。
- 评测报告同时输出分组正确率、拒绝准确率、失败类型、重试次数、延迟分布、模型 token 用量及成本估算。模型行为可能波动，关键用例要重复运行并展示波动范围。

**完成标准：** 一条命令能在隔离环境重跑当前版本；报告逐题列出结果和失败原因，明确当前基线；同样的用例与判分器可比较两个版本。

### 可观测：让一次请求的每一步可定位

- 在现有 `trace_id` 下记录查询运行、检索、规划、每次模型调用、SQL 校验、数据库执行、修复重试和报告生成。多步分析补 `run_id`、`step_id` 和尝试序号，事件保持父子关系与明确开始/结束状态。
- 每步记录耗时、结果数量、错误分类、模型名称、token 用量及配置版本；SQL 继续默认只存摘要，不把凭据、原始问题、完整结果或敏感 Prompt 写入普通审计日志。需要调试正文时采用显式开启、脱敏和限期保留。
- 管理员可以按追踪编号看到完整时间线，并查看聚合指标：成功率、拒绝率、错误分布、p50/p95 延迟、重试率与 token 用量。前端错误提示展示追踪编号，方便定位。
- 区分业务审计和技术诊断：审计回答“谁在何时访问了什么、是否被允许”，技术轨迹回答“哪一步耗时或失败”。定义保留期、访问权限和清理方式。

**完成标准：** 给出任意一次失败查询的编号，可以指出失败步骤、原因、耗时和是否执行了 SQL；并发请求之间的数据不串线，重启后已落库的记录仍可查询。

### 优化：用失败案例形成可复现的改进记录

- 先重跑历史报告中的 8 个结果不匹配用例，再根据当前评测重新分类：业务口径、Schema/指标检索、SQL 生成、权限策略、执行修复或报告解释。每类保留真实输入、预期行为和轨迹编号。
- 一次实验只改变一个主要因素，例如检索候选、Prompt 模板、指标知识或重试策略。保存变更前后的逐题结果和配置，避免无法判断提升来自哪里。
- 在调优集与保留集上都比较正确率，同时检查安全拒绝、延迟、token 和成本是否退化。失败案例进入回归集；没有显著收益或引入新的越权风险的改动不合入。

**完成标准：** 至少有一份可复跑的“问题归因 → 单点修改 → 全量回归 → 收益与代价”实验报告。只报告实际测得的数值，不预设提升幅度。

### 后端可靠性：承接真实的长任务

- 多步分析建立持久任务、步骤和事件序号，定义待执行、运行、成功、失败、取消等状态。浏览器断线后仍能查询任务状态和结果；重启后不能把未完成任务误报为成功。
- 限制并发和每个用户的资源占用；重复提交需要幂等处理，取消与超时须阻止后续 SQL。读取任务、事件、报告时再次校验当前用户权限。
- 将业务口径和数据源配置纳入可信后端：指标定义有版本，用户只能选择已授权的数据源，连接使用该数据源的只读账号。多企业隔离只有通过真实数据库账号与越权集成测试后才宣称完成。
- 扩展审计到授权变更、数据源配置、任务取消与报告访问；需要长期留存或多实例运行时再迁移到受控数据库，不把本地 SQLite 演示部署当作生产方案。

**完成标准：** 断开浏览器、重启后端、重复提交及权限变更的集成测试均能给出一致任务状态；未授权数据源和跨用户报告不可访问。

## 交付证据与实施规则

每完成一项能力，提交对应代码、必要的自动化测试和一份真实运行记录：使用的数据版本、模型与配置、执行命令、结果、失败案例和未验证范围。提交说明直接描述改动，不以“第几阶段”命名。

优先完成评测基线，再补技术轨迹，再做有数据支撑的优化。持久任务与企业数据源治理在前三项稳定后推进。前端只增加能够帮助用户理解运行状态与追踪编号的交互；不重做现有工作台。

不把增加框架、页面数量或模型调用次数当作成果。项目最终要能展示：一个真实失败如何被发现、定位、修复，并在安全、质量、延迟和成本之间得到可验证的结果。
