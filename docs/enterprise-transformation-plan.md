# ChatBI 后端能力完善规划

更新日期：2026-10-06。

## 当前决定

沿用原 React 页面及 `/api/v1/query`、`/api/v1/query/stream`、`/api/v1/analyze/stream` 接口。FastAPI 同时承担身份校验、业务编排、Agent 调用、SQL 安全执行和审计，不再引入另一套业务后端。已有 SQL 策略、统一执行器、只读数据库账号与资源预算继续保留。

浏览器只提交问题、会话及可选的数据源标识。用户身份和角色来自服务端验证的登录令牌，不能由请求体自报。所有模型生成的 SQL，包括多步分析和修复重试，都必须经过同一个 SQL 策略与执行入口。

## 已实现的基础

- 原有登录、注册待授权、管理员分配角色和区域，以及逐请求核验用户状态。
- SQL AST 校验、角色字段与表限制、销售区域范围约束、只读账号、行数/字节/时间预算。
- 单次查询、流式查询和多步分析共用受控执行器；用户会话按身份隔离。
- 每个 API 请求生成 `X-Trace-Id`。查询和分析事件、各次 SQL 执行使用同一编号；审计存于本地 SQLite，管理员可通过 `GET /api/v1/traces/{trace_id}` 查看。审计只保存 SQL 摘要、执行状态、身份、数据源、耗时和结果行数，不保存问题、SQL 正文或结果。

当前默认数据仍是新能源制造业演示数据。项目尚未具备完整多企业接入、独立数据源授权、正式任务恢复与报告版本治理；不能把演示配置当作已完成的 SaaS 隔离。

## 后续工作

1. 在 Python 内建立企业成员、数据源授权和凭据管理，先给数据源建立稳定标识与按企业授权，再让执行器仅从可信配置取得只读连接。跨企业隔离需用真实 MySQL 账号和集成测试验证。
2. 给问题补业务背景：指标定义、口径版本、所属企业、可用表与数据时间范围。Agent 的检索和 Prompt 只能看到当前用户获准的范围。
3. 为多步分析建立持久任务及事件序号，使浏览器断开后可查询任务状态和报告；任务取消、超时与权限变化必须在后续 SQL 步骤前重新检查。
4. 审计扩展为可检索的业务操作记录，覆盖授权变更、数据源配置与报告访问。需要长期留存时迁到受控数据库，并制定访问权限与保留期。
5. 用原有页面逐步展示数据源、业务口径和追踪编号；先保证现有查询交互可用，再增加管理界面。

每项能力以原前端到 Python 到只读 MySQL 的真实调用验证。功能测试之外，要检查越权 SQL 不触库、跨用户/跨企业不可读、重试不绕过策略、审计能串起同一次运行，以及中断后任务状态一致。
